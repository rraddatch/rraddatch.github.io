The path between source code and the screen reader

How HTML turns into the DOM, the accessibility tree, and finally into a screen reader's speech or braille output — and why that's not just "reading HTML".

Radoslav Ďurač · August 15, 2026 · about 20 min read

When a user works with a web page using a screen reader, it can look as if the assistive technology simply reads the HTML document. In reality, the path an information takes from the source code to its final presentation to the user through assistive technology is considerably more complex.

A screen reader generally doesn't work directly with the page's source HTML. Between the HTML document and the information the user ultimately receives, there are several layers. The browser parses the HTML and builds the Document Object Model, or DOM. Based on the DOM, the native semantics of HTML, ARIA, CSS and other information, it builds a representation intended for accessibility. It then maps that representation onto the accessibility mechanisms of the specific platform, through which the assistive technology accesses the information.

The assistive technology finally interprets the information it receives and presents it to the user, for example through speech or braille output.

Understanding this path has practical value for accessibility development and testing. It helps explain why an element can be present in the DOM without being exposed to assistive technologies, why the resulting accessibility representation can contain different information than the HTML source itself, or why the same implementation can behave differently across different combinations of browser, operating system and screen reader.

The goal of this article is to describe the path an information takes from HTML code through the DOM, the accessibility representation and platform accessibility APIs to the screen reader and its output to the user. This isn't a detailed account of how any specific browser or screen reader is implemented, but an explanation of the individual layers and their role in the overall process. Along the way, concrete examples show how HTML, ARIA and other attributes can affect the information that ultimately reaches assistive technologies.

1. HTML becomes the DOM

The first important step is the browser's processing of the HTML document. A browser doesn't treat HTML as plain text. While processing it, it builds a Document Object Model, or DOM for short. This model is defined by the DOM Standard.

The DOM is a programmatic representation of the document, arranged as a tree structure. Individual HTML elements become nodes within it, connected by hierarchical relationships. This representation also includes text nodes and information associated with each element.

Consider a simple document:

<!DOCTYPE html>
<html lang="en">
  <head>
    <title>My document</title>
  </head>
  <body>
    <h1>Heading</h1>
    <p>Paragraph</p>
  </body>
</html>

The browser builds a tree structure from it. The Document object contains the root element html. The html element has, in this example, two direct children, head and body. The head element contains title, whose text content is "My document". The body element contains an h1 element with the text "Heading" and a p element with the text "Paragraph".

So the DOM doesn't just capture the elements themselves. It also captures their hierarchical relationships. Every node can have a parent, children, and siblings at the same level of the tree. Text found inside elements is represented by text nodes.

The DOM is also a live representation of the document. JavaScript can change its content, add new elements, remove existing elements, or change their attributes. The current state of the DOM therefore doesn't have to match the original HTML the server sent to the browser.

It's important, though, to distinguish between the DOM and the representation intended for accessibility. The DOM is not the accessibility tree.

The DOM contains a lot of information needed for the page to function that isn't necessarily relevant to assistive technologies. Conversely, some information important for accessibility only arises during further processing of the document.

2. The DOM produces the accessibility representation

Based on the DOM, the native semantics of HTML, ARIA properties, CSS and other information, an internal representation of the content relevant to accessibility is created. In common terminology this is referred to as the accessibility tree.

The accessibility tree, however, isn't a simple copy of the DOM. It can be understood, in simplified terms, as a tree of objects relevant from an accessibility point of view. Individual objects can carry information such as their role, name, value, state, level, or relationships to other objects.

Native HTML semantics automatically provide a large part of this information. The <button> element provides button semantics. The <h1> element represents a level-one heading. A checkbox created with <input type="checkbox"> provides checkbox semantics and also allows its current state to be exposed.

CSS, meanwhile, can also decide whether an element appears in the accessibility tree at all. An element with display: none or visibility: hidden is excluded from the accessibility representation entirely, in the same way that its visual display and keyboard accessibility are also negated. This is a fundamental difference from aria-hidden="true", which we'll cover below: aria-hidden only hides an element from assistive technologies, while the element remains visually displayed and can still be focusable via the keyboard. This distinction is a common source of confusion during accessibility testing.

The way HTML elements and attributes are mapped onto platform accessibility APIs is described by HTML Accessibility API Mappings. More general mapping rules for web technologies onto platform accessibility APIs are described by Core Accessibility API Mappings.

The root object document can carry the name "My document", derived from the document's title. In the diagram it's also shown with the language en, derived from lang="en".

Under the document object, the diagram shows objects representing the heading and the paragraph.

The heading object has level 1 and the name "Heading". Beneath it there's also a text object with the text "Heading".

For the paragraph object, the situation is different. The object itself can have an empty accessible name, even though the paragraph contains the text "Paragraph". At first glance this might seem odd, since for the heading object we saw the name "Heading".

The reason is that an element's text content and an object's accessible name aren't the same thing. The fact that there is text between an HTML element's opening and closing tags doesn't automatically mean that text becomes the accessible name of that object.

What sources an object can get its accessible name from is decided, among other things, by its role and the accessible name computation rules. For individual roles, WAI-ARIA determines whether the name may come from the author or from the content. The computation itself is described by the Accessible Name and Description Computation specification.

For a heading, its text is also what identifies the heading. For the element:

<h1>Heading</h1>

the result can therefore be an object with the role heading, level 1, and accessible name "Heading". The text "Heading" can participate in computing the object's name.

For a paragraph:

<p>Paragraph</p>

the text "Paragraph" plays a different role. It's primarily the paragraph's text content, not its label. The paragraph object itself therefore doesn't need to have the accessible name "Paragraph". Its text nonetheless remains available in the accessibility representation as text content.

We can picture the difference in simplified terms like this:

<h1>Heading</h1>

heading
  name: "Heading"
  text: "Heading"

whereas:

<p>Paragraph</p>

paragraph
  name: ""
  text: "Paragraph"

An empty accessible name on the paragraph object therefore doesn't mean the paragraph is empty, or that its text isn't available to assistive technologies. It only means that, in this case, the text "Paragraph" doesn't represent the object's accessible name. The text content can be represented in the accessibility tree through a child text object and made available to assistive technologies that way.

This exact distinction is a good way to see why the accessibility tree can't be thought of as a DOM where HTML tags were simply renamed to roles. Building it involves the semantics of the individual elements and roles, and that semantics determines what properties the resulting objects will have and how their text content will be represented.

The diagram doesn't represent the one, normatively prescribed shape of the accessibility tree either. It's a simplified illustration of the principle. The actual tree structure and how individual objects are represented can vary depending on the browser, the platform, and the accessibility API used.

2.1 Not everything in the DOM has to be exposed in the accessibility tree

The DOM and the accessibility tree can differ not only in structure but also in which parts of the document they contain. The DOM can contain elements needed for visual display, page layout, or the functioning of the user interface, which from an accessibility point of view aren't meant to convey a separate piece of information to the user. Such elements therefore don't need to be exposed to assistive technologies.

One mechanism for excluding content from the accessibility representation is the aria-hidden="true" attribute. By using it, the author specifies that a given element and its descendants should not be exposed through the accessibility API. The element still remains part of the DOM and can still be visually displayed on the page. Details of the aria-hidden property are defined by WAI-ARIA.

When using aria-hidden="true", its effect on the element's descendants must also be taken into account. If a link, button, or other focusable element were located inside such a hidden section, it could remain reachable via the keyboard even though it isn't properly exposed to assistive technologies. aria-hidden="true" should therefore not be used on focusable elements or on their ancestors.

When testing accessibility, checking the DOM alone is therefore not enough. It's also necessary to verify the resulting accessibility representation and the information the browser exposes to assistive technologies through the platform accessibility API.

3. The accessible name isn't always the text we see in HTML

The accessible name is a text value that lets a user interface object be identified by assistive technologies. It doesn't necessarily come from a single specific HTML attribute or directly from an element's text content.

The browser computes it according to rules defined in the Accessible Name and Description Computation specification. Depending on the specific element and its role, various sources can feed into the computation.

For a form field, the name can come, for example, from an associated <label> element:

<label for="email">Email</label>

<input
  id="email"
  type="email"
  autocomplete="email">

In this case, the <label> element gives the field the accessible name "Email".

For a button, the name can come directly from its text content:

<button>Submit</button>

The button's accessible name in this case is "Submit". Other sources can also feed into its computation, such as aria-labelledby or aria-label, with the computation rules also determining their relative priority.

This can be shown well on a button whose visible text differs from the value of aria-label:

<button aria-label="Find">
  Search
</button>

The button contains the visible text "Search", which, without any other source, would provide its accessible name. In this case, however, the aria-label attribute is used, which takes priority over the button's text content when computing the accessible name. We can picture the result in simplified terms like this:

button
  name: "Find"

So the resulting accessible name "Find" is what's exposed to the assistive technology. The screen reader doesn't need to analyze aria-label itself and decide whether to prioritize it over the text "Search". That decision is already built into the accessible name computation rules, and the screen reader then works with the object's resulting property. It might announce something like "Find, button" to the user.

This example is purely to illustrate the accessible name computation mechanism, not a recommended way to write markup. A mismatch between a control's visible text and its accessible name violates WCAG 2.2 Success Criterion 2.5.3 Label in Name, since a voice-control user relying on the visible text "Search" might not be able to find the corresponding command. In practice, the accessible name should therefore contain the element's visible text, or at least extend it, rather than contradict it outright.

This example also shows why a screen reader's behaviour can't be reduced to "reading HTML". The information an assistive technology receives can be the result of processing multiple sources, and it doesn't have to match the text shown on screen.

The resulting representation can also be inspected in browser developer tools.

A view like this lets you check, during diagnosis, not just the HTML itself but also the resulting role, accessible name, description, states, and other properties the browser computed and exposes for the object.

3.1 The accessible name and the accessible description aren't the same thing

Alongside the accessible name, an object can also have an accessible description. These are two separate properties of the object in the accessibility representation, and each has a different role.

The accessible description provides supplementary information about an already-identified element. It might, for example, explain the required input format, the conditions for filling it in, or other information the user needs when working with the element. It doesn't replace the accessible name — it complements it.

Consider a form field:

<label for="password">Password</label>

<input
  id="password"
  type="password"
  autocomplete="current-password"
  aria-describedby="password-help">

<p id="password-help">
  Password must contain at least 12 characters.
</p>

In this case, the text "Password" from the associated <label> element is used to compute the field's accessible name.

The aria-describedby="password-help" attribute creates a relationship between the input field and the element with id="password-help". The text "Password must contain at least 12 characters." is therefore used to compute the field's accessible description.

We can picture the resulting object representing the form field in simplified terms like this:

textbox
  name: "Password"
  description: "Password must contain at least 12 characters."

So the text "Password must contain at least 12 characters." doesn't become part of the accessible name just because a screen reader might announce it together with the field's name. The accessible name and the accessible description remain separate properties of the object from the point of view of the accessibility representation.

This matters for testing too. If a screen reader, on focusing a field, announces something like "Password, edit field, Password must contain at least 12 characters", it may not be obvious from the speech output alone which property each piece of information came from. During diagnosis, it's therefore useful to check the resulting accessible name and accessible description directly.

The computation method for both properties is defined by the Accessible Name and Description Computation specification.

Role, accessible name and description are only part of the information an object can carry. Depending on the specific element, the accessibility representation can also contain its value, state, level, language, or relationships to other objects.

4. Accessibility APIs connect the browser to the operating system

The accessibility tree contains information about web content in a form relevant to accessibility. A screen reader, however, doesn't need to know about the DOM, or the way a specific browser internally builds and maintains this representation. It needs access to information about individual objects, such as their role, accessible name, state, or relationships to other objects.

Platform accessibility APIs exist to convey this information.

API is short for "Application Programming Interface". It's an interface that allows communication between different parts of software. In the case of an accessibility API, the platform provides a mechanism through which applications can expose information about their user interface to assistive technologies.

Consider, for example, a button that controls the display of a menu:

<button aria-expanded="false" aria-controls="menu">
  Menu
</button>

Based on the native semantics of the button element, its text content, and its ARIA attributes, the browser can build an object we can picture in simplified terms like this:

button
  name: "Menu"
  expanded: false
  controls: menu

The individual pieces of information come from different parts of the HTML. The button element provides the native button role, the text "Menu" is used to compute its accessible name, and aria-expanded="false" expresses that the controlled content is currently collapsed. The aria-controls="menu" attribute also creates a relationship to the element with id="menu", expressing that the button controls that content.

For assistive technologies to work with this information, the browser maps it onto the corresponding objects, properties, states and relationships of the specific platform's accessibility API. The button's role, its name, its expanded state, and its relationship to the content it controls all need to be represented in a way the given platform supports.

This mapping is necessary because web technologies and operating systems don't share a single common accessibility model. HTML and ARIA define the semantics of web content, while individual platforms have their own interfaces and their own ways of representing accessible objects and their properties.

There is therefore no single accessibility API shared across all platforms. On Windows, for example, Microsoft UI Automation is used; Apple's platforms provide their own Accessibility API; Linux desktop environments typically use AT-SPI; and Android provides its own Accessibility framework.

On Windows, it's actually more than a single API. Alongside UI Automation, the older IAccessible2 has long been used for exposing web content, and it's what browsers like NVDA and JAWS rely on heavily when working with web content. Chromium therefore supports both mechanisms simultaneously on Windows, and the specific screen reader chooses which one it works with.

So the browser has to expose the same web content semantics in a way that matches the platform it's running on. This mapping doesn't just involve object roles — it also covers accessible names and descriptions, values, states, relationships, and other information relevant to accessibility.

The rules by which web technology semantics are translated into platform accessibility APIs are described by the Accessibility API Mappings specifications. Core Accessibility API Mappings defines the general rules for mapping roles, states and properties, while HTML Accessibility API Mappings describes the mapping of HTML's native semantics.

So the accessibility tree and platform accessibility APIs serve different purposes. The accessibility tree represents web content from an accessibility point of view, while an accessibility API provides the interface through which that semantics can be exposed to assistive technologies on a specific platform.

5. In a modern browser, the whole process doesn't have to happen in a single process

Modern browsers are multi-process applications. Web content, the browser's own user interface, and other parts of its functionality don't necessarily run in a single shared process.

This kind of separation is mainly related to security, stability, and the isolation of different parts of the browser. A failure or problem on one web page therefore doesn't necessarily affect the whole browser.

A multi-process architecture also has consequences for accessibility.

The information needed to build the accessibility representation arises while the web document is being processed. Assistive technology, however, works with information exposed through operating system mechanisms. The browser may therefore need to transfer accessibility information between its internal processes and keep it synchronized across them.

Chromium is a good example; its accessibility architecture is described in more detail in the Chromium Accessibility Overview document.

One part of the browser may process the web document itself and build the information relevant to accessibility, while a different part exposes it through the operating system's accessibility API.

This doesn't mean that the entire DOM is simply sent to the assistive technology on every change. The browser maintains the necessary representations and updates the information that's relevant from an accessibility point of view.

If, for example, JavaScript changes an element's state:

<button aria-expanded="false" aria-controls="menu">
  Menu
</button>

to:

<button aria-expanded="true" aria-controls="menu">
  Menu
</button>

the change happens in the web document. The browser has to reflect it in its accessibility representation and make sure the object's new state is exposed through the relevant accessibility API as well.

Similarly, it may need to process a change to an object's accessible name, a form field's value, a checked state, keyboard focus, or dynamically inserted content.

Browsers use internal inter-process communication mechanisms to communicate between individual processes. Chromium, among other things, uses the Mojo infrastructure for this purpose.

Authors of web content don't need to know the details of this architecture. It is, however, important to know that between a change to HTML or the DOM and the information becoming available to assistive technology, there can be several further technical steps.

So an information can, along its path, pass through processing in the DOM, creation or updating of the accessibility representation, synchronization between parts of the browser, and mapping onto a platform accessibility API.

6. The screen reader further interprets the information it receives

A screen reader generally doesn't start at the page's HTML source code. It works with information made available to it by the platform, based on the representation the browser built.

If, for example, a user is focused on a button:

<button>Submit</button>

the screen reader might receive, through the accessibility mechanisms, information we can picture in simplified terms like this:

role: button
name: "Submit"
focused: true

This data still doesn't determine the exact sentence the user ultimately hears.

The screen reader has to interpret it and decide how to present it to the user. It can announce the element's name, its role, and, as needed, its state or other properties.

The output might have a meaning like:

Submit, button

The exact wording, however, isn't a property of the HTML or the accessibility tree. It depends on the screen reader, its localization, the user's settings, its mode of operation, and other circumstances.

This distinction matters. The accessibility tree doesn't contain a ready-made sentence for the screen reader to read. It contains structured information about objects. The screen reader builds the user-facing output from that information.

For an expandable button, it might, for example, have available:

role: button
name: "Menu"
expanded: false

From these properties it can build an output whose meaning is, for example:

Menu, button, collapsed

If the value of expanded changes to true, the screen reader might announce the new state to the user as "expanded". The way and the moment of that announcement, however, depend on the specific assistive technology.

A screen reader also doesn't just handle the presentation of the currently focused element. On top of the information exposed by the browser, it builds its own mechanisms for working with web content.

It might, for example, let the user:

  • move between headings,
  • move between links,
  • search for form fields,
  • navigate between tables,
  • display a list of certain types of elements,
  • read text by character, word, or line,
  • work with content without keyboard focus moving to every element.

This is why we also need to distinguish between the page's keyboard focus and the position where the user is currently located while reading content with a screen reader.

A user might, for example, move between headings or paragraphs, even though these elements themselves don't have to be focusable via the keyboard.

Related to this distinction is the announcement of content changes that aren't tied to a focus move, for example through aria-live. A region marked as aria-live can be announced by the screen reader to the user even when neither their focus nor their reading position is located in that part of the page. Here too, it's the specific assistive technology and its settings that determine the way and extent of such an announcement.

A screen reader can also let the user configure how much information is announced. Users can choose more detailed or more concise announcement of roles, states, and other properties.

The same object therefore doesn't have to be presented to different users in exactly the same way, even though the underlying information exposed by the browser stays the same.

When testing accessibility, it's therefore not a good idea to conflate the output of a specific screen reader with the accessibility representation itself. If a screen reader announces, or fails to announce, a particular piece of information, it's useful to distinguish whether:

  1. the information was correctly created in the HTML and the DOM in the first place,
  2. it was correctly reflected in the accessibility representation,
  3. it was correctly exposed through the accessibility API,
  4. and only after that, how the specific assistive technology works with it.

This kind of distinction helps you determine, during diagnosis, at which layer of the whole chain the problem is actually occurring.

Each of these layers can also be checked individually during diagnosis:

  • DOM – browser developer tools, the Elements panel.
  • Accessibility representation – the Accessibility panel in browser developer tools, or tools like Accessibility Insights for Web.
  • Platform accessibility API – for example Accessibility Insights for Windows or Inspect.exe on Windows, Accessibility Inspector on macOS.
  • Assistive technology output – for example Speech Viewer or the log in NVDA, which shows what was actually announced to the user.

If the result differs from expectations between two adjacent layers, the problem is most likely located right at the boundary between them.

7. The result isn't only synthesized speech

The term "screen reader" can create the impression that its output is always a voice. Synthesized speech is indeed a very common way of presenting information, but it isn't the only possible output.

A screen reader works with structured information about objects and can then convey it to the user in different ways. Most commonly this means speech output, braille output, or a combination of the two.

Speech output

For speech output, the screen reader prepares the information to be announced to the user and passes it to a speech synthesizer.

If it has, for example, the following object available:

heading
  level: 1
  name: "Heading"

it might convey information to the user whose meaning corresponds to something like:

Heading, heading level 1

The speech synthesizer then converts that information into audio form.

The resulting pronunciation can be influenced by several pieces of information. One of them is the language of the content.

If the document is correctly marked, for example:

<html lang="en">

the language information can become part of the accessibility representation, and the assistive technology can use it to select the appropriate pronunciation or voice.

So an attribute that originates in the HTML document can end up affecting the resulting speech output.

Braille output

Information doesn't have to be presented to the user by sound alone. A screen reader can also work together with a refreshable braille display.

A braille display is a hardware device made up of an array of braille cells with mechanically actuated pins. Individual pins rise and fall according to the characters being displayed, letting the user read the information by touch.

It's important to distinguish between the device and the mode of presentation. A braille display is the device, while braille output is the way information is presented to the user on that device.

If, for example, the page contains:

<p>Paragraph</p>

the text "Paragraph" can be conveyed to the user, through the accessibility representation and the screen reader, via speech output, braille output, or both simultaneously.

Braille output, however, doesn't have to be just a literal transcription of the speech output. A screen reader can build a separate representation of the information for the braille display, and use abbreviations or specific notations for roles and states.

The exact form of the braille output can therefore depend on the screen reader, its settings, the braille table used, the properties of the connected device, and other circumstances.

Information and its presentation aren't the same thing

At the end of the whole process, it's necessary to distinguish between the information made available to assistive technology and the way that assistive technology presents it to the user.

The browser and platform accessibility API might expose, for example:

role: heading
level: 1
name: "Heading"
language: en

The screen reader can use this data to produce speech output, braille output, or both simultaneously. It doesn't have to present all the available properties in the same way, or in the same order.

So HTML is not speech or braille output. The accessibility tree isn't a finished output for the user either. It's structured information that undergoes processing and mapping throughout its whole path, and only the assistive technology finally builds the resulting presentation for the user.

8. The quality of the whole chain starts in the code

The fact that there are several technological layers between HTML and the screen reader doesn't mean that a web content author needs to know the implementation details of every browser, operating system, and screen reader.

The most reliable starting point is using standard web technologies the way they were designed to be used, and following the rules and requirements of the relevant specifications so that the resulting code is valid.

Different ways of implementing the same user interface don't necessarily have the same level of support across every combination of browsers and assistive technologies.

A button, for example, can be built as a native HTML element:

<button>Save</button>

A component that looks similar at first glance can also be built like this:

<div role="button" tabindex="0">
  Save
</div>

These implementations, however, are not equivalent.

The native button element has its semantics, focusability, and basic interaction behaviour defined by HTML itself. With a generic div element, the author has to provide the necessary properties and behaviour themselves.

ARIA can add to or adjust the semantic information about an element, but on its own it doesn't recreate all the behaviour of a native HTML control.

When using ARIA, it's therefore a good idea to build on the principles described in Using ARIA and the ARIA Authoring Practices Guide.

8.1 Prefer native HTML elements (1st rule of ARIA use)

The first rule of ARIA use is also the most important one. If HTML provides an element or attribute that already has the required semantics and behaviour, it should be preferred over building a custom alternative with ARIA.

Instead of:

<div role="button" tabindex="0">
  Save
</div>

it's therefore better to use:

<button>Save</button>

The difference isn't just in the amount of code. A native button already provides semantics and basic behaviour that would otherwise have to be provided by the author for a custom component.

role="button" can affect how an object is exposed to assistive technologies, but it doesn't automatically turn a div element into a native HTML button.

8.2 Preserve the native semantics of HTML elements (2nd rule of ARIA use)

HTML elements already have their own semantics. If we override that with an ARIA role, the resulting representation of the object can start to diverge from its original meaning.

The following markup can be problematic, for example:

<h2 role="tab">
  Settings
</h2>

The h2 element has native heading semantics, while role="tab" assigns it a different role.

The Using ARIA document therefore warns that HTML's native semantics shouldn't be changed without a genuine need.

8.3 Ensure keyboard operability of interactive ARIA components (3rd rule of ARIA use)

If an author builds a custom interactive component with ARIA, it isn't enough to ensure its correct representation for assistive technologies alone. The corresponding interaction behaviour must also be implemented.

For example:

<div role="button" tabindex="0">
  Save
</div>

can be focusable and exposed with the button role. That alone, however, doesn't ensure it will behave like a native button.

For a custom element with role="button", the author also has to implement the expected keyboard interaction. The ARIA Authoring Practices Guide for the Button Pattern describes activating a button with the Enter and Space keys.

A native button provides this basic behaviour automatically. For a custom component, the author is responsible for implementing it.

8.4 Expose focusable elements to assistive technologies (4th rule of ARIA use)

Another rule warns about a conflict between an element's focusability and its removal from the accessibility representation.

The following markup is problematic, for example:

<button aria-hidden="true">
  Continue
</button>

The same problem can also arise indirectly:

<div aria-hidden="true">
  <button>Continue</button>
</div>

In the second case, aria-hidden="true" also applies to the descendants of the parent element. An interactive element can then end up in a situation where it's part of the keyboard interaction but isn't properly exposed to assistive technologies.

aria-hidden="true" should therefore not be used on focusable elements, nor in a way that removes their focusable descendants from the accessibility representation.

8.5 Give interactive elements an accessible name (5th rule of ARIA use)

An interactive element needs not only a correct role and behaviour, but also a name through which the user can understand its purpose.

For example, an icon button with no text content:

<button>
  <svg aria-hidden="true">
    ...
  </svg>
</button>

can have the correct native button role and be operable via the keyboard, yet without further information it might not have a usable accessible name.

One possible solution is:

<button aria-label="Close">
  <svg aria-hidden="true">
    ...
  </svg>
</button>

In this case, aria-label gives the button the accessible name "Close", while the icon itself is hidden from assistive technologies.

Even here, though, the basic principle applies that ARIA should be used where it's actually needed. If a button already contains suitable text, its accessible name can be derived from the native content without adding aria-label.

8.6 Prefer native semantics and behaviour over a custom implementation

The more semantics and behaviour native HTML provides, the less responsibility remains with the author of a component. With a custom ARIA component, the author has to make sure, on their own, that the visual appearance, declared role, current state, keyboard behaviour, and the information ultimately exposed through the accessibility API all match — and even a technically correct implementation doesn't guarantee identical behaviour across every combination of browser, operating system, and assistive technology.

Use the semantics and behaviour that HTML itself provides first, and add ARIA only where it's genuinely needed.

The path from HTML to voice therefore doesn't start in the screen reader. It starts with the author's decision about which element to use in the source code.

Good semantics creates the foundation from which a meaningful accessibility representation can arise. Through platform mechanisms, that representation can be exposed to assistive technology and ultimately presented to the user through speech or braille output.

Author: Radoslav Ďurač, Bratislava, Slovakia.
